# Project Sovereignty Contract

This project must preserve its core product meaning and critical operating capability if an external provider, API, SDK, model, connector, runtime, or vendor disappears or materially changes.

- Project-owned contracts define canonical inputs, outputs, errors, authority, state, evidence, and completion semantics.
- External providers are adapters, not project identity.
- Critical dependencies are `REPLACEABLE`, `DEGRADED_FALLBACK`, `HARD_DEPENDENCY`, or `UNKNOWN`.
- Critical capability needs an alternate adapter, local/open implementation, deterministic fallback, export/manual recovery path, or honest safe degraded mode unless a documented hard dependency is explicitly accepted.
- Critical data keeps project-owned semantics and a migration/export path.
- Provider swaps must not broaden authority, replay stale approvals, duplicate mutations, or weaken evidence requirements.
- Provider outcomes map into project-owned receipts; provider acceptance is not outcome proof.
- When operated through Founder Control Room, this remains a sovereign subsystem, not a separate founder OS.

## Federated continuity quartet

Sol Continuity works with Founder Control Room, Chief AI Machine, and PromptOS as a federation of sovereign systems. Cooperation happens through verified state, fingerprints, proof cookies, and receipts. Authority does not move merely because continuity does.

- **Sol Continuity** carries assistant/model/session continuity and capability-routing state across tools, models, and adapters.
- **Founder Control Room** owns consequential founder-control execution, approval binding, provider/runtime mutation, and verified operational receipts.
- **Chief AI Machine** owns reasoning, capability composition, challenge, governance interpretation, and test-ledger evidence for Chief-owned behavior.
- **PromptOS** compiles founder intent into prompt/workflow structure without creating execution authority.

Sol must never treat conversation history, model memory, a peer fingerprint, or a proof cookie as sufficient proof of current repository/runtime state. Before material action, re-resolve the authoritative target repo/head, provider/runtime state, evidence contract, and local authority ceiling.

### Bidirectional cookie rule

For material work involving any quartet peer:

```text
receive peer fingerprint / proof cookie
→ verify exact source repo + branch + head
→ compare subject / runtime / provider / evidence / authority dimensions
→ invalidate stale or contradictory continuity
→ act only inside current local authority
→ re-observe the real outcome
→ emit successor fingerprint / proof cookie + receipt
→ return it to affected peers
```

Continuity cookies are non-secret state/evidence markers. They are never browser cookies, credentials, bearer tokens, approval tokens, merge tokens, deploy tokens, publish tokens, or standing mutation authority. They cannot replay founder approval.

Movement in source or target repo head, subject, scope, authority, runtime, provider, evidence requirement, or founder proposal expires the affected present-tense marker until revalidated. Preserve predecessor markers as historical provenance.

Verified evidence may update or invalidate Sol's stale route, capability fingerprint, proof cookie, assumption, or next gate. Evidence alone does not mutate external systems. Under current founder approval bound to the exact proposal, and only when the target system's own gates allow it, that evidence may support the smallest reversible repair, implementation, stale-proof correction, issue reconciliation, or forward action.

After an approved mutation performed through an authorized capability, Sol must re-read authoritative state, verify the actual outcome, and emit a successor marker linked to its predecessor. If the result is not proven, export `UNKNOWN`, `BLOCKED`, `STALE`, or `CONTRADICTED`, never a synthetic green state.

Mandatory audit question: **If every named provider disappeared now, what stops, what survives, what is the recovery path, and what evidence proves it?**

Use: Reality → ULTRATHINK → Redteam I → Lindy → L99 → OODA → smallest reversible implementation → focused proof → Redteam II/provider-loss attack → rollback → next gate.
