# Founder Intelligence Agent Entry Point

Every AI agent working in this repository must preserve SolContinuity's repo-native authority, exact-head verification, and separately gated live Devnet evidence before making material planning, implementation, review, release, deployment, package-publishing, credential, or production claims.

## Canonical challenge stack for nontrivial SolContinuity work

```text
ULTRATHINK
→ Red Team 1 — premise
→ Lindy mode
→ L99
→ Red Team 2 — implementation
→ OODA
→ Proof
→ Rollback / Next Gate
```

- **ULTRATHINK:** reconcile continuity goals, repository truth, exact-head state, Solana/Devnet boundaries, package/runtime evidence, and competing implementation paths before selecting a bounded problem frame.
- **Red Team 1:** challenge the premise, evidence, scope, and whether the requested continuity or resilience change should exist.
- **Lindy mode:** prefer the smallest durable, reversible repo-native carrier and stable protocol/interface over novelty or duplicated state.
- **L99:** bind the selected path to current subject fingerprints, provenance, state, scoped authority, evidence requirements, release/package state, rollback, continuity, and drift.
- **Red Team 2:** attack the chosen implementation for authority inflation, stale evidence, protocol regressions, unsafe provider assumptions, package/runtime drift, hidden assumptions, overclaims, and missing recovery.
- **OODA:** observe the exact current repository/runtime state, orient to SolContinuity's local and live-evidence boundaries, decide one bounded action, act only within current authority, then re-observe and verify.
- **Proof / Rollback / Next Gate:** keep local test, CI, package, Devnet, hosted runtime, and production truth separate; record rollback and the smallest next gate.

A failed pass narrows, changes, or stops the work. These modes coordinate one founder intent and never grant package publication, deployment, credential, production, spending, destructive-mutation, or live Devnet authority.

## Portable Juss OS command surface

```text
/goalfix
/ultrathink
/truthmode
/confess
/redteam
/lindymode
/ooda
/visualize
```

- `/goalfix`: diagnose one concrete failure and choose the smallest coherent evidence-backed fix that satisfies the full correctness boundary.
- `/ultrathink`: expand the option space, reconcile constraints, and identify the highest-leverage evidence-backed path.
- `/truthmode`: separate `VERIFIED`, `INFERRED`, `UNKNOWN`, and `BLOCKED` claims against inspected repository, test, and runtime evidence.
- `/confess`: expose unsupported assumptions, stale evidence, missing inspection, and overclaimed certainty.
- `/redteam`: challenge the premise, the proposed change, and the selected implementation for failure modes or authority inflation.
- `/lindymode`: prefer durable, reversible, low-dependency primitives over novelty and brittle coupling.
- `/ooda`: observe, orient, decide, act within current authority, verify, and define the next loop.
- `/visualize`: translate verified state into a diagram, plan, or explanation only. It does not mutate the dashboard, providers, Devnet, package registry, infrastructure, or production state.

These commands are reasoning, planning, and routing modes only. They never expand execution authority. They do not authorize package publication, hosted API/dashboard deployment, credential registration or rotation, production routing, destructive mutation, spending, or live Devnet evidence.

Local tests and CI prove only the scopes they actually execute. Live Solana Devnet resilience evidence remains a separate founder-gated runtime witness and must not be inferred from local or CI success.

SolContinuity `main`, the repo-local Control Room, exact-head verification, rollback/evidence rules, and separate founder gates remain stronger authority. If a portable command conflicts with a stricter repository rule, the stricter rule wins.

## Project-owned delivery and applicable skills

For every authorized creation or repair, leave the corresponding project able to continue without this chat or a disposable workspace.

- Resolve the actual project, repository, branch, current head, existing owner, and applicable agent instructions before changing anything. Discover and invoke all relevant, available, approved skills required for that task; do not load unrelated skills merely to claim “all skills.” Record skill execution honestly as unavailable, inspected, invoked, or verified, and name any blocking requirement.
- Deliver created code, configuration, images, video, workflows, and reusable knowledge to their authorized project-owned destination. Prefer the existing implementation and asset pipeline. Local scratch files, a chat response, a generated preview, a copied skill, or an unconnected registry entry are not completed project implementation.
- When the task requires executable behavior, connect the deliverable to the project's actual entrypoint/runtime or existing adapter. Include the necessary dependencies and configuration references, focused verification, operating instructions, failure handling, and rollback. Keep credentials outside source control. If runtime integration is not applicable, explain why; if it is blocked or separately gated, leave an explicit incomplete state and next gate rather than claiming it works.
- For image/video and design tasks, resolve project-scoped approved references from GitHub, Canva, Figma, and ChatGPT Library when authorized and available. Preserve source identifiers, versions, approval scope, and content hashes in the appropriate private or public-safe project record. Missing access is a named gap, never permission to search unrelated content. A generated variant, world/ensemble board, source location, or matching hash does not by itself grant character-canon approval.
- Keep each product independent. Reuse another project's approved contract through a scoped interface; do not copy its private data, identity, proprietary prompts, or authority. This rule does not make this project a media renderer or enable a provider/runtime by declaration.
- Leave a minimized handoff with goal, affected paths, exact branch/commit, intended versus applied changes, tests and results, observed runtime outcome versus unknowns, source/artifact hashes where relevant, rollback, and next owner/gate. New evidence supersedes only its bound subject; preserve historical provenance.
- Documentation changes are instructions, not machine enforcement or proof of live behavior. This rule grants no additional search, sharing, publication, spending, deletion, merge, deployment, secret, auth, or provider-mutation authority. Preserve all stricter project and founder gates, including current restrictions on new PRs/drafts.
